## Preface

An exemplary implementation of the Language Server Protocol (LSP) in **Go**.
This project demonstrates how modern IDE features work by developing a custom language server for a custom domain-specific language called **Flow**.  
The implementation uses a parser generated by Tree-sitter. Fortunately, Tree-sitter generates not only the parser but also associated bindings for various languages, including Go.
In addition, the Go package github.com/tree-sitter/go-tree-sitter was used, which offers a range of functionalities for using such a parser.

Other dependencies, such as ready-made implementations of the protocol or similar, were deliberately avoided, as the goal of this project is to understand the LSP and abstractions from third-party libraries would therefore be counterproductive.

First, a few basic terms will be explained, along with why the technologies used were chosen:

### Language Server
A language server is responsible for various language-specific functions (code intelligence tools) and works independently of the editor. A number of common tasks performed by a language server are:

- Code completion (IntelliSense): Suggests suitable code elements during input.
- Error and warning diagnosis: Highlights errors and potential problems directly in the code.
- Code navigation: Helps find definitions and references to symbols.
- Formatting: Automatically formats the code according to specific rules.



### Purpose of the LSP
The Language Server Protocol (LSP) serves to standardize communication between a text editor or IDE acting as a client and a language server. This allows a single language server to be developed for a programming language, which can then be used by many different editors that implement the LSP.
This standardization solves the “M-by-N problem,” where a special solution had to be developed for each combination of editor and language. Furthermore, it decouples all language analysis tasks from the editor's user interface.
The exact specification can be found [here](https://microsoft.github.io/language-server-protocol/specifications/specification-current).

### Go for language server development
Language servers are often started on demand by editors or run multiple times in parallel. Go programs start extremely quickly, require (usually) little RAM, and have a low CPU footprint.
In addition, cross-compilation is offered out of the box, and the single statically linked binary significantly simplifies distribution.



### Client/Server Communication
Unlike traditional web servers, language servers typically do not communicate via TCP/HTTP, but rather via standard input (stdin) and standard output (stdout).

This means:
1. The editor (client) starts the language server process.
2. Request: The editor writes the JSON-RPC messages directly to the stdin of the running Go process.
3. Response: The Go process writes its responses to the stdout.
4. The editor reads stdout and processes the response.

Since this is a continuous data stream, the server needs to know when a message ends. Similar to HTTP, the LSP uses a Content-Length header for this purpose.
```
Content-Length: 154\r\n
\r\n
{
    “jsonrpc”: “2.0”,
    ...
}
```



### Tree-sitter
Tree-sitter consists of two main components: the parser generator and an incremental parsing library that creates syntax trees for source code and updates them efficiently when changes are made. It enables programs such as editors or language servers to not only analyze the code line by line, but also to obtain a structured, tree-like representation and query it using so-called Tree-sitter queries.

Incremental parsing makes it possible to efficiently update the syntax tree when small changes are made to the source code, instead of rebuilding it from scratch. Tree-sitter can also parse temporarily faulty code by isolating errors so that the rest of the file is processed and displayed correctly. 

Tree-sitter generates a concrete syntax tree (CST), which contains all the syntactic details of the source code. Abstract syntax trees (AST), on the other hand, abstract from these details, as they focus only on the logical and semantic structure of the code. For example, an AST would not represent the semicolon at the end of a statement or the parentheses around a condition. Tree-sitter was developed primarily for editor and tooling purposes (syntax highlighting, code folding, intelligent navigation, refactoring), which is why the exact position and presence of each token in the source code is crucial.

Tree-sitter uses a [generalized left-to-right algorithm (GLR)](https://en.wikipedia.org/wiki/GLR_parser) internally to perform the parsing process. GLR is an extension of the classic [LR parser (bottom-up parser)](https://en.wikipedia.org/wiki/LR_parser). While traditional LR parsers can only process unambiguous (non-ambiguous) grammars, GLR enables the parsing of ambiguous grammars.

### **FlowLang**

FlowLang is a minimal (proof-of-concept) DSL for defining data pipelines. The individual components of a typical Flow file are as follows:

The language allows you to define where the data comes from (source):  
```hcl
source "raw_user_data" {  
    path: "/data/users.csv"  
    encoding: "utf-8"  
}
```

what types of processing are applied to this data (task): 
```hcl
task "filter_active_users" {  
    # takes the raw_user_data source output
    input: raw_user_data  
    transformer: "filter_by_column 'status' == 'active'"  
}
```

and where the data is transported to (sink): 
```hcl
sink "active_user_report" {  
    # takes the filter_active_users tasks output
    input: filter_active_users  
    path: "/reports/active_users.json"  
}
```


### The grammar (EBNF)
The grammar has been deliberately kept simple; explicit precedence rules and complex conflict resolution (ambiguities) have been avoided.  

```
source_file       ::= { definition }

definition        ::= source_definition | task_definition | sink_definition

source_definition ::= "source" string_literal source_body
source_body       ::= "{" { source_prop_path | key_value_pair } "}"

task_definition   ::= "task" string_literal task_body
task_body         ::= "{" { prop_input | prop_transformer | key_value_pair } "}"

sink_definition   ::= "sink" string_literal sink_body
sink_body         ::= "{" { prop_input | sink_prop_path | key_value_pair } "}"

source_prop_path         ::= "path" ":" string_literal
sink_prop_path         ::= "path" ":" string_literal
prop_input        ::= "input" ":" identifier
prop_transformer  ::= "transformer" ":" string_literal

key_value_pair    ::= identifier ":" value
value             ::= string_literal | identifier | number | boolean
```



### **Implemented features**

1. [Contextual Hover](https://github.com/david-hass/lsp-introduction/blob/main/server/hover.go) (textDocument/hover)
   When the mouse pointer is moved over keywords such as sink, task, etc., the user receives textual information about the syntax.
   The language server uses the cursor position to determine which node in the syntax tree is affected and, based on its type, which text information must be delivered to the client.
3. [Semantic diagnostics](https://github.com/david-hass/lsp-introduction/blob/main/server/diagnostics.go) (textDocument/publishDiagnostics)  
   The server checks logical references. For example, if a task that has not been defined is used as input, this is marked as an error.
   When opening or changing a document, the language server first collects the definitions, then the references, and then compares them with each other.



### **Build & Installation**

The project was developed in the following environment:

* Linux (Manjaro 6.16)  
* Go 1.25.1  
* npm 11.6.1  
* gcc 15.2.1


1. #### Generate the Grammar (optional)

    The C code for the parser is already located in server/parser/. If changes are made to the grammar (grammar/grammar.js), it must be regenerated:  
    ```
    cd grammar  
    npm install  
    npx tree-sitter generate && npx tree-sitter build  
    ```
    Afterwards, the files must be copied manually to ../server/parser/.  
    Alternatively, use the script: ../server/copyparser.sh


2. #### Build the server

    The server must be compiled so that the clients can start it.  
    ```
    cd server  
    go mod tidy  
    CGO_ENABLED=1 go build -o flow-lsp
    ```
    
    **Test:** Run ./flow-lsp. The server should start and wait for input. In addition, a log file should have been created under /tmp/flow\_lsp.log (under Windows usually %TEMP%\\flow\_lsp.log) with the following content:  
    ```
    2025/11/27 12:29:21 --- flowlang server started ---
    2025/11/27 12:29:21 tree sitter parser loaded.
    2025/11/27 12:29:21 flow tree sitter parser loaded
    ```



### **Integration in Neovim**

Integration could take place as follows using lazy.nvim / nvim-lspconfig.  
Insert the following into mason-lspconfig config() and adjust as necessary:  
```
local flow_lsp_path = vim.fn.expand("~/projects/lsp-introduction/server/flow-lsp")
local util = require 'lspconfig.util'

vim.lsp.config.flow = {
  cmd = { flow_lsp_path },
  filetypes = { "flow" },
  root_dir = util.find_git_ancestor() or util.path.dirname,
  capabilities = capabilities,
}
vim.lsp.enable('flow')
```
Facing Problems? Have a look here: ``:h lsp-config``



### **Integration in VS Code**

The VS Code client is located in the vscode/ folder.  
**Install dependencies:**  
```
cd vscode  
npm install
```

1. In VS Code, execute the command: Developer: Install Extension from Location...  
2. Then select the vscode folder from this repository
3. Now open the VS Code settings and search for “flow.”  
4. Under **Flow: Server Path**, enter the absolute path to your flow-lsp binary
